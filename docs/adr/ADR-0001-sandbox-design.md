# ADR-0001　IDP Sandbox 的设计（Agent 执行沙箱）

| 项 | 内容 |
|---|---|
| 状态 | 已接受（2026-11-06；决策人选择新建独立仓库 `idp-xyz/idp-sandbox`，方案由实现者推荐） |
| 范围 | `idp-sandbox`：让 Agent 在隔离环境里运行自己写的代码，并保存结果文件 |
| 依据 | idp-host ADR-0001 D1（HOST 不内建工具，工具都经 MCP 网关）与 D31（不使用厂商自带的 code interpreter，因为它绕过逐个工具调用的门控）；idp-mcp ADR-0001（上游由 Release 钉住、授权与审计在网关）；MCP 2026-07-28 |

## 1. 背景与边界

此前平台里没有"Agent 执行代码"的能力：HOST 的 harness 只能经网关调用已登记的工具。让模型写代码并运行，是一类常见的需求（数据处理、计算、格式转换），但也是风险最大的一类：模型的输出就是不可信代码，可能被提示词注入操纵。

这个组件只做一件事：给不可信代码一个**没有网络、资源有限、用完即弃**的运行环境。它不做：长期运行的服务、持久数据、包安装、GPU、交互式终端。

## 2. 决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **做成 MCP 上游服务，放在 idp-mcp 网关后面，不内建进 HOST** | HOST 的 D1 / D31 已定：工具都经网关。这样沙箱免费得到网关的授权（哪个角色能用哪些工具）、按钉住的 `inputSchema` 做参数校验、调用审计、漂移封锁和四眼发布；HOST、Workspace 一行都不用改 |
| D2 | **每次运行一个全新的容器**：无网络、只读根、用户 65534、丢弃全部 capabilities、`no-new-privileges`、seccomp、私有 IPC、`init`；内存（含交换）、CPU、进程数、`nofile`、`fsize`、墙钟时间、输出大小都有上限 | 没有状态可以泄漏到下一次运行；每一项对应一类已知的滥用（外联与渗出、提权、fork 炸弹、内存与磁盘耗尽、死循环、输出洪水） |
| D3 | **隔离后端可替换**：默认 Docker（runc，加固）；`IDP_SANDBOX_RUNTIME=runsc` 或 `kata` 用 gVisor / Kata；`Backend` 是接口，Kubernetes Job 后端见 D12 | runc 与宿主共享内核，对真正不可信的代码不够；换运行时应当只是配置 |
| D4 | **工作区 = 有大小上限的 tmpfs 卷**（内核执行配额），由一个很小的"锚"容器（`sleep`，4 个进程、16 MiB）持有 | 配额不是应用层的估算，满了就是 ENOSPC；文件只在内存里，工作区一删就没有了。Docker 的 local 卷驱动在没有容器使用时会卸载 tmpfs 并丢掉内容，所以需要锚（实现时踩到的，见 §4） |
| D5 | **文件读写走容器的标准输入输出，不走归档 API** | tmpfs 卷只在挂载它的容器的挂载命名空间里可见，`docker cp` 的归档 API 写进去的东西运行时看不到（实测）。读取用 `[ -f ] && [ ! -L ]` 与 `readlink -f` 拒绝符号链接与越界 |
| D6 | **调用方只能缩短，不能放宽**：镜像、语言、资源上限都是运维配置；调用方能选的是语言（枚举）、代码、超时（不超过上限）、路径（相对、无 `..`、不进 `.idp/`） | 沙箱的价值在于调用方（可能被注入的模型）改不了约束 |
| D7 | **工作区属于调用者**（D11）；id 仍是 128 位随机数；一次只允许一个运行；有总数、每个调用者与并发数的上限；空闲 30 分钟与存活 4 小时后回收；启动时按标签清扫上一个进程遗留的容器与卷 | M1 时网关不转发身份，id 只能是承载令牌；M2 起有了身份，id 是第二道防线 |
| D11 | **调用者身份来自网关（M2，idp-mcp ADR-0001 D40–D43）**：沙箱在 idp-mcp 里以 `identity: forward` 注册；网关把经过认证的 tenant、subject、roles 放进每个请求的 `_meta["io.idp.telos/caller"]`，并总是先删除客户端自带的同名键。沙箱把工作区绑到 `tenant/subject`：别的调用者（包括另一租户的同名用户）对它的任何操作得到的都是"不存在"，与一个从未存在的 id 不可区分；每个调用者最多 8 个工作区；请求不带身份就拒绝（`IDP_SANDBOX_REQUIRE_CALLER`，默认开） | 多租户、多用户共用一个沙箱实例不再依赖 id 的保密；按调用者限额才有意义；审计里有"谁"（subject 的哈希前缀） |
| D8 | **自己没有认证，只接受网关**：默认只监听回环；监听非回环地址必须设置 `IDP_SANDBOX_PRIVATE_NETWORK=true`（运维声明只有网关能到达） | 与 idp-mcp 的"上游在私网"一致；宁可启动失败，也不要被一个 `0.0.0.0` 的默认值暴露一个能执行代码的端口 |
| D9 | **审计只记元数据**：工具名、结果、耗时、工作区 id 的哈希前缀、代码的 SHA-256 前缀；不记代码与文件内容。内部错误（容器引擎的报错、路径）不返回给模型，只写日志 | 代码里可能有敏感数据；引擎错误会泄露部署细节 |
| D10 | **依赖：只用标准库**（Engine API 走 unix 套接字上的 net/http，附着标准输入用 HTTP 升级的原始连接）；MCP 的准入规则从 idp-mcp 复制，不共享代码 | 与 HOST 的 D13 相同 |
| D12 | **Kubernetes 后端（M3）**：同一个 `Backend` 接口，只用 Kubernetes REST API（net/http）。工作区是 PVC；每次运行是一个 Job（`backoffLimit 0`、`activeDeadlineSeconds`、Pod 的加固与 D2 一一对应：非 root、只读根、丢弃 capabilities、seccomp、不挂令牌、requests = limits）；没有 exec，所以代码与文件放进 ConfigMap 挂载，结果从 Pod 日志读，stderr 靠包装命令与随机标记分开；无网络由运行命名空间里的 NetworkPolicy 保证，服务与运行分在两个命名空间，服务账号在运行命名空间只有最小的 Role，另有 ResourceQuota 与 LimitRange | 套接字等于宿主 root（§5）；Job 后端让沙箱不再需要容器引擎，并能用 RuntimeClass 换 gVisor / Kata。没有 exec / attach，是为了 RBAC 里不授予它们：服务账号被攻破时也不能进入别人的运行 |
| D13 | **经白名单的出口代理（M3）**：运行默认没有网络；运维配置了出口代理（`idp-sandbox-egress`，`IDP_SANDBOX_EGRESS_PROXY`）时，`sandbox_run` 多一个 `network` 参数，取 `none`（默认）或 `egress`。`egress` 的运行得到自己的、`Internal` 的网络（没有网关、没有路由出去），网络上只接着代理（用完即断开并删除），并设置 `HTTP_PROXY` / `HTTPS_PROXY`。代理按**主机名**白名单（精确名或 `*.后缀`，空表示全部拒绝）和端口白名单放行 CONNECT 与明文 HTTP 转发，并**自己解析、自己检查地址**：回环、私网、链路本地（含 169.254.169.254）、CGNAT、多播、未指定地址一律拒绝，所以白名单里的名字指向内网、或 DNS 重绑定，都进不去；有并发数、隧道时长和字节数上限，每次放行与拒绝都记日志 | 不能联网就不能装包、调 API，这是真实需求；放开必须是运维的决定、有边界、可审计。每次运行一个网络，是因为共享网络里并发运行（可能属于不同调用者）能互相连接。`network` 参数让工具的 schema 变化，网关钉住 schema，所以启用出口要重新发现并评审服务器（这是想要的）；没配置代理时 schema 里 `network` 只有 `none` |
| D14 | **office 运行档位（平台 ADR-0002 阶段 0，2026-11-13）**：运维用 `deploy/office/build.sh` 构建镜像 `idp-sandbox-office:<版本>`，即 python 运行镜像加上 [OfficeCLI](https://github.com/iOfficeAI/OfficeCLI)（Apache-2.0）的 linux-x64 单文件二进制。版本与 SHA-256 钉在脚本里（现为 1.0.159，2026-10-27 发布，与 release 的 SHA256SUMS 和 GitHub API 摘要都对过）；构建用 `--network none`，构建后在同样的限制下冒烟一次。设了 `IDP_SANDBOX_OFFICE_IMAGE` 才出现 `language: office`：在这个镜像里以 POSIX shell 运行脚本，`officecli` 在 PATH 上，隔离与限额和其他运行完全相同，调用者仍不能选镜像（D6）。`sandbox_run` 的 `language` 参数带上每种语言的说明，模型能据此选择。镜像的环境变量与原因：`OFFICECLI_SKIP_UPDATE=1`、`OFFICECLI_NO_AUTO_INSTALL=1`（运行没有网络）；`OFFICECLI_NO_AUTO_RESIDENT=1`（默认 `create` 会在后台起常驻进程缓存文档，运行一结束它就随容器消失，未写回的修改会丢，还占进程配额）与 `OFFICECLI_RESIDENT_FLUSH=each`（Agent 仍会显式 `officecli open`，它自带的参考资料推荐这样做，真实模型实测就这么做了：每次修改立即写回，常驻进程随运行消失也不丢东西）；`DOTNET_EnableDiagnostics=0`（不在 `/tmp` 建调试管道与诊断套接字）；`DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1`（镜像没有 ICU，不设则 .NET 启动即退出；只影响按地区的格式与排序，不影响中文等文字本身）；`DOTNET_EnableWriteXorExecute=0`（.NET 的 W^X 双重映射用 `ftruncate` 给一个内存文件定大小，而运行的文件大小上限 `fsize` = 工作区配额同样限制它：8 MiB 时实测 `PAL_SEHException` 中止，64 MiB 时通过；关掉它，档位就不依赖工作区配额的大小。代价是 JIT 代码页不再写执行分离，进程本身仍在无网络、只读根、无能力、seccomp 的隔离里） | Agent 要读、改、生成 Word / Excel / PowerPoint 文件；OfficeCLI 不需要 Office，单文件、离线可用。它的 MCP 模式是 stdio 服务器（`officecli help` 所述），不适合直接登记为网关上游（平台 ADR-0002 第 1 节），所以以命令行的方式放进沙箱，沿用沙箱的全部隔离 |
| D15 | **成员文件的进出（平台 ADR-0002 阶段 1，2026-11-13）**：运维设了 `IDP_SANDBOX_FILES_URL`（Workspace 的内部文件端点）才多出两个工具。`sandbox_import_file {workspaceId, source, path}` 把成员附在这次请求上的文件拷进工作区；`sandbox_export_file {workspaceId, path, target, name?}` 把工作区里的文件交给成员，成员在这次请求上看到并下载，结构化结果是 `deliveredFile {ref, name, size, sha256, mediaType}`。模型写的是 `attachment:1`、`output` 这样的占位，参数的 `format`（`idp-attachment`、`idp-delivery`）告诉 idp-host 哪个参数收文件（idp-host D37），它在模型这一轮之后、调用到达网关之前换成 Workspace 为这次运行签的票据（读票据指向一个文件，写票据允许交付），所以模型和网关的调用记录里都没有票据，字节只在沙箱与 Workspace 之间走，不经过模型。沙箱不验签（Workspace 验签名、受众与过期），只先看票据的 `tenant_id`/`sub` 是不是这次调用的调用者、种类对不对，不是就不去 Workspace（纵深防御）。两个方向都检查文件（`internal/files.Check`）：扩展名在白名单里（.docx .xlsx .pptx .pdf .png .jpg .jpeg .csv .txt .md），带宏的格式（.docm .xlsm .pptm 等）与包里的 `vbaProject.bin` 拒绝，内容要与扩展名相符（魔数；文本须是 UTF-8 且无 NUL），Office 包限 10000 个部件、解压后 256 MiB、单部件压缩比 200、部件名不能越出包；交付的文件名只留一个路径元素。单个文件上限 `IDP_SANDBOX_TRANSFER_MB`（默认 25，不得大于工作区）。读票据出示一次就用掉（idp-workspace D27），所以导入先确认工作区是调用者的、路径合法（`Manager.CanPut`），再去 Workspace 取：工作区 id 或路径写错不会白白用掉附件；第二次导入时把 Workspace 的话原样交给模型（"已经拷进过工作区，接着用那一份"）。Docker 后端：字节经标准输入进（D5），出则从附着流读，不经日志驱动（见第 4 节），`sandbox_read_file` 也改为从附着流读。Kubernetes 后端起初不提供（ConfigMap 与 Pod 日志不能原样搬二进制，配了 `IDP_SANDBOX_FILES_URL` 时服务拒绝启动），2026-11-17 起由 D19 提供 | 阶段 0 只能生成文件，成员拿不到，也给不了自己的文件。让模型经 `sandbox_write_file` 传 base64 会把整个文件塞进上下文、调用记录和网关审计，25 MiB 的文件根本放不进；票据让字节绕开模型，换占位让票据也不进模型和网关的记录 |
| D16 | **office 档位增加 `sheetskel`（2026-11-17，配合 idp-host D41）**：镜像里多一个只靠标准库的 `/usr/local/bin/sheetskel`。`sheetskel FILE.xlsx` 打印每个工作表的名字、使用范围、表头和下一行，张数、列数和总长度都有上限。构建仍是 `deploy/office/build.sh` 的 `--network none`，不把 openpyxl 或别的第三方包装进镜像。`language: office` 的说明里写明用它看现成的工作簿，而不是自己拆包 | 报价表那次运行把九十多步花在用 Python 的 zipfile 拆 xlsx、反复打印上。缺的是一次就能看到表结构的命令，不是一个通用表格库。openpyxl 要在构建时联网或把轮子钉进仓库，而这条命令用标准库就够，也进不了运行时的安装 |
| D17 | **office 档位读 PDF、写 PDF、处理 Markdown（2026-11-17；决策人选定"读 PDF、生成带中文字体的 PDF"，Word / Excel / PowerPoint 转 PDF 不做）**：镜像增加五个 wheel、两个字体文件和字体的许可文本，逐个按 SHA-256 钉在 `deploy/office/build.sh`，下载后校验，`pip install --no-index --no-deps` 装入并以 `pip check` 确认没有缺的依赖，构建仍是 `--network none`。读：pypdf 6.21.4（BSD-3-Clause），加 pycryptodome 4.3.0，pypdf 用它打开 AES 加密的文件。写：reportlab 5.1.0（BSD）及其声明的依赖 Pillow 13.0.0 与 charset-normalizer 3.5.2。字体：Noto Sans SC 2.004 的常规与粗体（Google Fonts 的静态 TrueType 文件，SIL OFL 1.1），连同 `OFL.txt` 放在 `/usr/share/fonts/truetype/noto/`。两个命令：`pdftext FILE.pdf` 按页打印文字，默认至多 12,000 字节、至多读 12 秒，停下时写明接着读的命令；`--pages`、`--layout`（保留横向位置，表格的一行仍是一行）、`-o`（写入文件，不限大小）、`--password`、`--check`（只报页数，打不开则退出码 1）；没有文字层的页写明是扫描件、这里没有 OCR。`md2pdf IN.md OUT.pdf` 把 Markdown 排成 A4 的 PDF：标题、段落、列表、表格、围栏代码、引用、分隔线、链接、本地 PNG / JPEG 图片、页脚页码；中文用内嵌的 Noto Sans SC；九列以上的表格转横向；`--dump` 只输出读到的结构。`language: office` 的说明里写了这两个命令，所以 `sandbox_run` 的 schema 变了：已经在运行的部署升级沙箱服务后，要在网关重新 discover、评审、发布（D16 改说明时同样如此） | 文件通道本来就收 `.pdf` 与 `.md`（D15），镜像里却没有任何能读写 PDF 的程序，也没有一个字体文件。Markdown 是纯文本，读写不需要工具。模型最顺手的输出就是 Markdown，所以"生成 PDF"做成"写 Markdown，一条命令排版"，不让它每次自己写排版脚本、自己找字体。reportlab 只内嵌 TrueType 轮廓的字体，Noto CJK 发行版是 OpenType（CFF），所以取 Google Fonts 的静态 TrueType 版。没有选 PyMuPDF（AGPL）与 fpdf2（LGPL，同样要 Pillow）。pypdf 与 pycryptodome 没有取最新版（7.1.0 发布才 4 天，4.5.0 才 2 天），取的是发布满两周的版本。读取有字节与时间上限，是因为模型读到的工具结果至多 16 KiB（idp-host D40），一次运行默认 20 秒；说明里写明下一条命令，模型不用猜怎么接着读 |
| D18 | **调用者要有网关的签名（2026-11-17，idp-mcp ADR-0001 D44）**：设了 `IDP_SANDBOX_CALLER_KEYS_FILE`（网关的公钥，PEM，P-256，可以放几把）与 `IDP_SANDBOX_CALLER_AUDIENCE`（本服务在 idp-mcp 里登记的端点，如 `http://sandbox:8570/mcp`）之后，每个 `tools/call` 必须在 `_meta["io.idp.telos/caller-assertion"]` 里带网关签的断言。沙箱检查：ES256、`typ` 是 `idp-caller+jwt`、`kid` 是它持有的公钥、签名验得过、`aud` 是自己、没过期（允许 30 秒时钟差，有效期超过 5 分钟的不收）、`req` 等于它自己对这次请求算出的摘要、`jti` 没见过。通过后调用者取自断言，`io.idp.telos/caller` 那份没签名的不再看；不通过则 403，原因只写日志，工具不运行。`tools/list` 与 `server/discover` 不需要调用者（网关的漂移检查没有调用者）。只设其中一个变量则拒绝启动；两个都没设时行为同 D11，启动时写一条告警。验签只用标准库（D10），规范化 JSON 的规则从 idp-mcp 复制 | D11 把工作区绑在调用者上，而调用者是一段谁都能写的 JSON：沙箱的网络上任何能连到 8570 的东西都能自称任何人，读走那个人的工作区。有了签名，网络策略从"唯一的边界"变成"第二层"。`req` 与 `jti` 让截获的断言既不能换成别的调用，也不能把同一个调用再发一次 |
| D19 | **Kubernetes 后端也搬任意内容的文件（2026-11-17）**。没有 exec，也没有通到 Pod 的字节流，所以两个方向各用一种它本来就能做的事。**进**：文件切成每块 1,000,000 字节（API 服务器对一个 ConfigMap 的键与值合计限 1 MiB），每块一个 ConfigMap（`binaryData`），用一个 projected 卷把它们按 `c00000`、`c00001` … 挂进同一个 `file` Job，`cat` 拼成文件并核对字节数，写不全就删掉；ConfigMap 随 Job 一起删除。大文件的写入在服务内串行（一次几十个 ConfigMap，而运行命名空间的配额是 48 个）。**出**：第一个 Job 报文件大小与 SHA-256；不超过 3 MiB 的文件在同一个 Job 里以 base64 打进日志，更大的由后续 Job 每个读 3 MiB（`dd` 加 `base64`），至多 3 个同时进行；拼回后核对 SHA-256，对不上就是"文件在读的过程中变了"。每个 Job 都先做 Docker 后端那两条检查（是普通文件、`readlink -f` 仍在 `/work` 里）。后端实现 `BinaryFiles` 与新的 `BinaryReader`（`sandbox_read_file` 仍走原来读日志的路径，它只读文本）；`MaxWriteBytes` 是后端自己的上限，超过就不碰集群。服务账号的 Role、命名空间的配额都没有改 | 成员的文件此前只能走 Docker 后端，而 Docker 后端要容器引擎套接字（第 5 节）；想用 Job 后端、想用 Kata 的部署就没有文件通道。base64 是因为 Pod 日志是文本：容器运行时按行存、kubelet 按大小轮转，原样打二进制会坏（Docker 后端在第 4 节踩过同一个坑）。3 MiB 一块：base64 之后连同运行时给每行加的前缀约 6.5 MiB，在 kubelet 默认的 10 MiB 日志文件之内，不会被轮转掉。不给服务账号加 `pods/exec`、不起一个常驻的文件中转 Pod：D12 不授予 exec 的理由没有变，常驻 Pod 则要在运行命名空间里开一个能进出的口子 |

## 4. 实现中发现的

- **归档 API 写不进 tmpfs 卷**：先用 `docker cp` 写文件，运行时文件不在。卷在没有容器挂载时被卸载，即使有运行中的容器，`cp` 也写到了卷驱动之外。改为经标准输入写入（D5），并让一个锚容器持有卷（D4）。
- **经网关的上游需要进注册服务的主机白名单**（`IDP_ALLOWED_UPSTREAM_HOSTS`、`IDP_PRIVATE_UPSTREAM_HOSTS`）：沙箱是私网主机，开发拓扑的覆盖文件里已加。
- 日志驱动不能设为 `none`（读不到输出）；用 `json-file` 并限制为 1 MiB。
- **日志不能原样搬文件**（阶段 1 发现）：`sandbox_read_file` 原来从容器日志取 `cat` 的输出，而 `json-file` 日志驱动按行存为 JSON 字符串，非 UTF-8 字节会被替换，超过 1 MiB 还会轮转丢掉前面的部分。.docx 是 zip，读回来就坏了。改为在启动前附着容器（`stdin=0` 时只要输出），从附着流读，帧格式与日志相同，不经日志驱动（`TestBinaryFilesMoveUnchanged`：3 MiB 随机字节含 NUL、CRLF、非法 UTF-8，进出不变）。

## 5. 限制（没有做的，以及为什么）

- **runc 共享宿主内核**：加固挡不住内核漏洞。生产应使用 gVisor 或 Kata。Docker 后端的 `IDP_SANDBOX_RUNTIME=runsc` 实测过（见下，含文件进出与 office 档位）；`IDP_SANDBOX_RUNTIME=kata` 只有代码、没有实测（Kata 只在 Kubernetes 后端测过）。默认值仍是守护进程的默认运行时，也就是 runc：换运行时是运维的一行配置，不是默认行为。
- **服务需要容器引擎套接字，那等于宿主的 root**。开发拓扑挂载 `/var/run/docker.sock`；生产应在专用节点、虚拟机或 rootless 引擎上运行，或加套接字代理限制 API；或用 Kubernetes 后端（D12），那里服务账号的权限就是一个 Role。
- **身份这一跳的签名要配置才有**（D18）：没设 `IDP_SANDBOX_CALLER_KEYS_FILE` 时，网关转发的身份没有签名，沙箱靠"只有网关能到达它的私网"相信网关（idp-mcp D43），网络策略就是边界。设了之后仍有三件事没做：公钥靠运维放文件，没有自动轮换；`jti` 表在内存里，重启后的一分钟内同一个断言能再用一次（重启同时清空工作区，所以能重放的只是对空沙箱的调用）；连接可以是明文 HTTP，断言不防窃听。Kubernetes 清单里这两项配置是注释掉的，没有在集群上验证过：`tests/kind/check.py` 不经网关、直接带一个调用者调用沙箱，接上签名需要它自己会签。
- **出口只有 Docker 后端有**（D13）：Kubernetes 后端的运行仍然完全没有网络；等价的做法（白名单代理 Pod 加只放行它的 NetworkPolicy）未做。出口代理按主机名放行；白名单可以按租户分（D21），不按人或角色分。代理能看到并记录目标主机，看不到 HTTPS 的内容；放行的主机若允许上传，就能被用来外传工作区里的数据，所以白名单应当只列只读来源。
- **按租户的出口（D21）没有做的**：
  - 租户的真实性来自转发的调用者。没有配网关签名（D18）时，能到达沙箱端口的任何东西都能自称任何租户，也就能用任何租户的白名单；按租户分白名单的部署应同时配 D18。
  - 凭据只约束"哪张名单"，不约束名单里的主机能做什么：同一租户的两个人到得了同样的主机，能上传的主机仍然是外传通道。
  - 凭据可以被运行里的代码读到并带出去。它在过期前、在代理地址相同的另一个运行网络上仍然有效（Docker 会把刚释放的网段再分出去）。这需要原租户的代码主动把凭据交出去，而那样的代码本来就能替别人取回任何它到得了的内容，所以没有再加一次性或与容器绑定的校验。
  - 名单是代理启动时读的文件，改了要重启代理；没有管理接口，也没有让租户管理员自己维护名单的界面。
  - 客户端必须把代理地址里的用户名和密码作为 `Proxy-Authorization` 发出去，否则得到 407。实测的只有 Python 的 urllib（明文与 CONNECT）和 Go 的 net/http；requests、pip、curl、wget 按它们的文档也这样做，没有在运行镜像里逐个试。
  - 开发拓扑的 `--profile egress` 只渲染检查过配置，没有随 `deploy/e2e.sh` 跑；平台的 compose 与 Kubernetes 清单都没有接出口代理。
- **加固运行时的实测情况（2026-11-06）**：
  - **gVisor（runsc 20260126.0，`kvm` 平台）**：Kubernetes 后端在 kind 上 22 项集群检查全过，整平台 PATH D 也过——但那次的内存炸弹是靠超时过的：kind 用 systemd cgroup 驱动，runsc 没开 `systemd-cgroup` 时把 Pod 的 cgroup 路径当成目录名，沙箱跑在 Pod 的 cgroup 之外，运行的内存与 CPU 上限都没生效（256 MiB 的 Pod 分配 2 GiB 不被杀）；开了之后沙箱回到 Pod 的 cgroup，但整个沙箱在 pause 容器的 cgroup 里，kubelet 只给容器关 swap，节点有 swap 时炸弹会先换进 swap（5 次里 2 次拖了 10–17 s 才被杀），所以 `tests/kind/gvisor.sh` 同时给所有 Pod 关了 swap，之后内存炸弹 4.5 s 被 OOM 杀掉，`check.py` 也改成超时不算通过；Docker 后端 20 个隔离测试全在 runsc 下，全过（`tests/integration/gvisor.sh`，docker-in-docker，容器用宿主 cgroup 命名空间时 runsc 能应用 cgroup：内存炸弹被限额杀掉，fork 炸弹耗尽进程数上限、整个沙箱被杀；`CGROUPS=0` 退回 `--ignore-cgroups` 时上限不生效、靠超时挡住）。默认的 `systrap` 平台在这台 WSL2 上起不来（最新 20261102.0：`creating process: out of memory`；20260126.0：`failed to create a syscall thread`），`kvm` 与 `ptrace` 可用，根因没有查；这个环境里所有进程（含节点的 PID 1）都带一个 seccomp 过滤器，可能相关。gVisor 的 `--pids-limit` 数的是沙箱自己的宿主线程，16 起不来，64 可以。与 runc 的差别：`/proc/self/status` 没有 `NoNewPrivs` 与 seccomp 行，写只读根得到 EACCES，`--network none` 的沙箱连回环网卡都没有（更严），Docker 内置 DNS 在其网络栈里不生效（出口代理的地址因此按 IP 给）。
  - **gVisor 下的文件进出与 office 档位（2026-11-17 补测）**：上面的 20 个用例是文件通道（D15）与 office 档位（D14、D16、D17）之前测的。`tests/integration/gvisor.sh` 现在在给了 `IDP_SANDBOX_OFFICE_IMAGE` 时把 office 镜像也装进 docker-in-docker，并按 release 的 sha512 校验下载的 runsc。同一台机器、runsc 20260126.0、`kvm` 平台、宿主 cgroup 命名空间：24 个用例全部通过、没有跳过的，共 92 秒。新增的四个：`TestBinaryFilesMoveUnchanged`（3 MiB 随机字节进出不变，3.7 s）、`TestOfficeDocumentsInTheOfficeProfile`（.NET 单文件二进制在 gVisor 里新建、修改、校验 Word / Excel / PowerPoint，16.4 s）、`TestOfficeDocumentsRoundTrip`（6.1 s）、`TestPDFAndMarkdownRoundTrip`（7.0 s）。所以"成员的文件进出沙箱"这条路径可以整条跑在 gVisor 上，代价是服务仍然要容器引擎套接字。没有测的：这四个用例在 `systrap` 平台和真实（非嵌套）节点上的表现；平台的 compose 没有装 runsc，PATH J 仍在 runc 上。
  - **Kata（4.3.1，Go 运行时 + Cloud Hypervisor）**：Kubernetes 后端 22 项全过（`tests/kind/kata.sh`），客户机内核 6.18.56；内存型 `/tmp` 在客户机里没有大小限制，写满撞 Pod 内存上限被 OOM 杀，而不是 ENOSPC。QEMU 在这台机器（WSL2 嵌套 KVM）上客户机一启动就崩；Rust 运行时需要节点里没有的 D-Bus。
  - **性能（Python 3.12，同机）**：docker 上 runc 对 runsc：CPU 密集相同；4000 个小文件读写 0.07 s 对 0.15 s；10 万次 `stat` 0.06 s 对 0.55 s；300 MB 内存触碰 0.12 s 对 0.49 s；容器启动 340 ms 对 640 ms。Kubernetes 上 runc / gVisor / Kata：Pod 从创建到完成约 3.7 s / 5–8 s / 8 s；4000 个小文件 0.18 / 0.17 / 2.5 s（Kata 走 virtiofs）；`stat` 0.06 / 0.56 / 0.05 s；300 MB 内存触碰 0.12 / 0.5 / 0.55 s。
  - **没有验证的**：PVC 容量是否被存储驱动执行（kind 的 local-path 不执行；云块存储的卷大小本身就是上限）、镜像摘要锁定与私有仓库拉取、生产 CNI 的行为、真实（非嵌套）云节点上的 gVisor / Kata。**部署的集群必须有执行 NetworkPolicy 的 CNI**（kind 默认的 kindnet 在 CI 里没有拦住运行 Pod 的出站，验证用 Calico），否则"无网络"不成立。D20 起服务启动时自己探测一次，2026-11-17 实测：kind v0.31 自带的 kindnet（kindnetd v20251212-v0.29.0-alpha）上，全拒策略已经应用，与运行同标签的 Pod 仍然连得上 API 服务器（10.96.0.1:443），探测报告"连得上"，服务不会启动；Calico v3.30.3 上同一个探测 6.6 秒后报告"连不上"，服务启动，日志有一行 `run pods are cut off from the network`。`Pids` 无法按 Pod 设置（交给 kubelet 的 `podPidsLimit` 或 gVisor）；stderr 在超时被杀时丢失；每次文件操作启动一个 Pod（秒级）。
- **Kubernetes 后端搬文件的代价与边界**（D19；2026-11-17 在 kind v0.31 单节点上实测，WSL2）：
  - **慢**：每一步是一个 Job，Pod 启动就要 3 秒左右。runc：3 MiB 以内的文件写入 3–4 秒、读回约 3 秒（一个 Job）；25 MiB（上限）写入 5.4 秒、读回 18.9 秒（1 个报大小的 Job 加 9 个读块的 Job，3 个并行）。gVisor：25 MiB 写入 6.1 秒、读回 20–21 秒。Kata（Cloud Hypervisor，客户机内核 6.18.56）：8.0 秒、27.8 秒。网关默认 60 秒的调用超时之内，但余量不大；节点更慢或文件上限调大时要一起调 `IDP_CALL_TIMEOUT`。
  - **导入时 etcd 里短暂放着整份文件**：25 MiB 是 27 个约 1 MB 的 ConfigMap，Job 结束即删；大文件的写入在一个服务实例内串行，所以同时最多一份。
  - **导出依赖 kubelet 的日志文件上限**：每块 3 MiB 是按默认的 `containerLogMaxSize` 10 MiB 定的。上限调小了的节点会在一块之内轮转日志而丢数据；拼回后的 SHA-256 对不上，报"文件在读的过程中变了"，不会把坏文件交给成员，但那样的节点上大文件导不出来。
  - **读的过程中文件不能变**：没有快照。一次运行在导出期间改写了同一个文件，导出报错，agent 重试即可。
  - **没有测的**：多节点与真实云集群；PVC 满了时的行为（kind 的 local-path 不执行容量）；平台的 kind 清单还没有把文件通道接起来（Workspace 内部监听的 Service、沙箱到它的 NetworkPolicy、网关重新发现两个新工具，`deploy/kubernetes` 里只有注释掉的配置），所以经平台的 PATH J 仍只在 compose 上走过。
- **启动探测（D20）只说明启动那一刻**：只连 API 服务器一个地址，只在启动时做一次。之后有人删了策略、换了 CNI，服务不会知道；到外网、到别的 Pod 的连接由同一条策略管，但没有逐个去探。辅助镜像没有 `nc` 时 `enforce` 下服务不启动。
- **单实例、内存里的工作区**：重启即清空；没有跨副本的会话。
- **没有按调用者的配额与计费**：只有全局的并发与工作区总数上限。
- 只有 Python 与 Shell 两种语言；镜像里没有额外的库（要数据分析库就得由运维构建带库的镜像并配置）。
- **PDF 与 Markdown（D17）没有做的**：扫描件（没有文字层的页）读不出文字，没有 OCR。Word / Excel / PowerPoint 不能转成 PDF：officecli 的 `view … pdf` 回答"No exporter plugin found"，镜像里没有导出插件，也没有装 LibreOffice，它能否在一次运行的限额内工作没有测过。`md2pdf` 没有斜体（字体没有斜体字形，斜体按正体排），不认脚注、定义列表与 HTML 块，图片只收本地的 PNG / JPEG；段落里几种字体混排时，行首偶尔会出现逗号、句号。`pdftext` 不认列与列之间的关系，表格要靠 `--layout` 保住每一行。
